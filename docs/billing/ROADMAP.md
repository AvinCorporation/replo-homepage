# 자동결제 운영·사용성 로드맵

2026-09-14 · 우선순위 기준: 금액 사고 가능성 → 고객 이탈 가능성

이 문서는 자동결제 MVP 코드 리뷰에서 확인한 고객 여정과 운영 과제를 실행 순서로 관리합니다. 완료 표시는 Git에 구현과 검증이 함께 반영된 경우에만 변경합니다.

## 카드 운영 원칙

- Workspace마다 활성 Toss 카드는 **주 카드 1개 + 백업 카드 1개**, 최대 2개입니다.
- 첫 등록 카드는 주 카드, 두 번째 등록 카드는 백업 카드가 됩니다.
- owner/admin이 백업 카드를 주 결제수단으로 바꿀 수 있으며, 전환은 한 DB 트랜잭션과 감사 로그로 남깁니다.
- 기존 주 카드에 결과가 확정되지 않은 승인이 있으면 결과 반영 전까지 전환을 차단합니다.
- Worker는 주 카드만 사용합니다. 백업 카드는 별도 고객 동의 없이 자동 대체 승인하지 않습니다.
- 카드 등록 실패 시 기존 주 카드와 백업 카드는 그대로 유지합니다.
- 카드 삭제·교체와 자동 대체 승인 정책은 별도 확정 후 구현합니다.

## Phase 0 — 자동 승인 활성화 전

- [ ] `billing_events` 기반 결제 실패·최종 실패·카드 등록 완료 이메일
- [ ] `billing.charge_requires_review`, 장기 reconciliation, 고아 빌링키 정리 실패의 Sentry 또는 Slack 알림
- [ ] 기술 오류 10회 차단·미납 Invoice 조회와 `billing_approve_arrears_retry`를 제공하는 최소 운영자 화면

고객 알림 수신처는 `customers.billing_email`을 사용하되, 발송 전 주소 유효성과 수신 정책을 확인합니다. 알림 이벤트에는 `notified_at`, 발송 결과, 재시도 횟수를 남겨 중복 발송을 막습니다.
